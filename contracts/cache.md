# Cache contract

Lab 5 adds a shared, sharded cache for frequently read data and for authentication data. Each owner caches **its own** reads and invalidates them on **its own** writes. The cache is spread over three nodes with **consistent hashing**, so losing a node only empties that node's share of the keys.

Status: **proposed** (Lab 5).

## Nodes

| Node | Address | Image |
| --- | --- | --- |
| `cache-1` | `cache-1:6379` | `valkey/valkey:8` |
| `cache-2` | `cache-2:6379` | `valkey/valkey:8` |
| `cache-3` | `cache-3:6379` | `valkey/valkey:8` |

- The nodes are **independent**: no Valkey replication or cluster mode. Sharding is done by the clients (see [the ring](#consistent-hash-ring)).
- No persistence (`--save "" --appendonly no`) and `maxmemory 128mb` with `allkeys-lru` eviction. The cache only holds copies, so a restart just empties it.
- The nodes are on the internal network only and require a password (`CACHE_PASSWORD`, generated by `lab.py setup`).

Every service gets `CACHE_NODES=cache-1=cache-1:6379,cache-2=cache-2:6379,cache-3=cache-3:6379` and `CACHE_PASSWORD`. The ring uses the **logical names** (`cache-1`), not the addresses, so changing a port never moves keys.

## Pattern: cache-aside

1. **Read.** `GET key`. On a hit, decode and return it.
2. **Miss.** Read the owner's database, then `SET key value EX ttl`, then return the value.
3. **Write.** After the database transaction **commits**, `DEL` every key the write changed. Never update a cached value in place; the next read refills it.

Rules:
- **Delete after commit.** Deleting before the commit lets a concurrent read put the old value back.
- **TTL backstop.** Every key has a TTL plus 0–10 % random jitter, so a lost `DEL` only means stale data until the TTL ends, and hot keys don't all expire at once.
- **The cache never fails a request.** A connection error, timeout (50 ms per command) or decode error counts as a miss and is logged as `cache unavailable` at most once per 10 seconds per node. Writes still commit, and a failed `DEL` is logged and left to the TTL.
- **Only the owner writes its keys.** A service may read and delete only keys that start with its own service name. Other services' data is never cached directly, except for the [auth data](#authentication-data) below, which is keyed under the caller's own name.
- **Values** are the JSON that the owner's route would return (UTF-8), at most 64 KiB. Larger results are not cached.
- **Never cached:** mutations, `Idempotency-Key` replays, anything containing secrets (passwords, raw refresh tokens, device tokens), and paginated pages after the first.

## Key format

```text
{service}:v1:{resource}:{id}[:{id}...]
```

Examples: `tamagotchi:v1:pet:{petId}`, `user-management:v1:session:{sha256(refreshToken)}`. The `v1` segment changes when the cached shape changes, which invalidates every old key at once.

## Authentication data

Gateway verifies access tokens locally with User Management's keys, so verifying a token needs no lookup. The lookups that happen on almost every request are cached instead:

| Data | Who caches | Key | TTL | Deleted when |
| --- | --- | --- | --- | --- |
| Refresh session | User Management, on `POST /v1/auth/refresh` and `logout` | `user-management:v1:session:{sha256(refreshToken)}` | the session's remaining lifetime, at most 1 h | the token is rotated or revoked |
| User by ID (status, roles) | User Management | `user-management:v1:user:{userId}` | 5 min | profile, role or status change |
| Enrollment check `GET /internal/v1/users/{userId}/packages/{packageId}` | **the caller** (Tamagotchi, Notification and any other caller) | `{caller}:v1:enrollment:{userId}:{packageId}` | 60 s; a negative answer (`404`) 10 s | a caller that already consumes `user.package-registered.v1` (Tamagotchi) deletes the negative entry when the event arrives |

- Only the SHA-256 of a refresh token is ever used as a key; the token itself is never stored in the cache.
- Enrollments are only ever added, so a cached positive answer can't go stale. A negative answer is cached for just 10 s, so a fresh enrollment shows up within 10 s even for callers that don't consume the event. No new topic subscriptions are needed.
- Revoking a session deletes its key **before** answering, so a revoked token can't be refreshed from the cache.

## Consistent-hash ring

Every client places keys with the same algorithm. Test vectors: [cache-ring-vectors.json](cache-ring-vectors.json).

1. **Points.** For each node `n` in `CACHE_NODES` and each `i` from 0 to 159, compute `point("{n}#{i}")`, where `point(s)` is the first 4 bytes of `MD5(UTF-8 s)` read as a big-endian unsigned 32-bit integer. Three nodes give 480 points.
2. **Sort** the points in ascending order (ties, which don't occur for our names, go to the lexicographically smaller node).
3. **Lookup.** Compute `point(key)` and take the first ring point whose position is `>=` it. Past the last point, wrap to the first. That point's node owns the key.
4. **Unavailable node.** While a node's client is failing (3 errors within 10 s; it's retried after 5 s), skip its points and continue clockwise to the next point of an available node. Its keys therefore land on its neighbours, and every other key stays where it is.

**Why 160 virtual nodes.** With one point per node, the arcs between points are very uneven. With 160 per node, the 30,000 benchmark keys in the vectors file split 35 % / 32 % / 33 %. When `cache-2` is unavailable, exactly its own 9,668 keys move, and none of the others.

Each owner implements the ring in its language: about 40 lines, plus a test that loads `cache-ring-vectors.json` and checks every `node` and `nodeWhenCache2Down`. Reference implementations for Go and TypeScript ship in the Message Broker repository's client kit (`clients/go/cache`, `clients/ts/cache`), next to the Lab 4 broker clients, and can be copied as they are.

## Consistent hashing compared with Redis Cluster

Lab 5 asks for consistent hashing. Redis Cluster, the ready-made alternative, shards differently:

| | Our ring (consistent hashing) | Redis Cluster (hash slots) |
| --- | --- | --- |
| Mapping | Key → position on a 2³² ring → first virtual node clockwise → node | `CRC16(key) mod 16384` → slot → node, from a slot table |
| Who computes it | Every client, from the node list alone | The cluster owns the slot table; clients cache it and follow `MOVED`/`ASK` redirects |
| Adding or removing a node | About 1/N of the keys move automatically; no coordination | An operator or tool reassigns slots, and the cluster migrates their keys |
| Node failure | Its keys become misses on the neighbours; fine for a cache | A replica of the failed primary is promoted, if replicas are configured; without one, its slots are unavailable |
| Balance | Statistical, improved by virtual nodes (160 here) | Exact: slots are split evenly by count |
| Multi-key operations | Only when the keys happen to share a node; we use none | Only within one slot; hash tags `{…}` force keys together |
| Setup in Compose | Three plain Valkey containers | Six nodes (3 primaries + 3 replicas) plus a cluster-create step |

Both avoid the `hash mod N` problem, where changing N moves almost every key. Hash slots are a **fixed partitioning**: 16384 partitions that move between nodes as whole units. Consistent hashing moves **ranges of the ring** implicitly whenever the node set changes. For a cache that may simply lose data, the ring is simpler and needs no coordinator.

## Observability

- Every cached read logs `cache hit` or `cache miss` at debug level with `key`, `node` and `requestId`, and each service exports `cache_requests_total{result="hit|miss|error", node}` on its existing metrics.
- `GET /status` adds `cache: {nodes: [{name, available}]}`.
- Demo: read a pet twice (miss, then hit on its node), stop `cache-2`, and read again. Only keys that lived on `cache-2` miss, and nothing errors.
